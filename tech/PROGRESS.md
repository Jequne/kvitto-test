  зависимости.
- `tech/PROGRESS.md` — состояние нового слайса.

### Архитектурные решения

- Роуты получают `PaymentService` одной зависимостью; `AsyncSession` используется
  только в фабрике зависимости и репозитории. Сервис принимает контракт
  репозитория и работает с доменными объектами и командами.
- Скидка вычисляется в целых копейках с промежуточным `Decimal` и округлением
  половины вверх до копейки. Остаток рассрочки распределяется по первым взносам.
- Вставка платежа использует уникальный ключ идемпотентности PostgreSQL и
  `ON CONFLICT DO NOTHING`; запись платежа и графика фиксируется одной
  транзакцией в `get_session`. Сервис и репозиторий не выполняют `commit()`;
  репозиторий делает `flush()` для графика, чтобы платёж читался до фиксации.
- При успешном завершении запроса `get_session` вызывает `commit()`, при ошибке
  — `rollback()`. Для маршрутов с сессией установлена область зависимости
  `function`, чтобы завершить транзакцию до отправки HTTP-ответа.
- `PaymentService.create()` возвращает именованный `CreatePaymentResult`.
  Репозиторий получает `created_at` через `INSERT ... RETURNING` и возвращает
  новый доменный платёж без повторного чтения по ID. При конфликте ключа
  существующий платёж читается отдельно.
- Неизвестный тариф или неизвестный/неактивный промокод возвращает 422.
  При повторе ключа возвращается сохранённый платёж с HTTP 200.

## Слайс 7. Обработка банковского webhook

Принят пользователем после проверки Swagger, БД и согласования двух тестов
webhook. Коммит запрошен пользователем.

### Созданные и изменённые файлы

- `src/kvitto_test/domain/payment.py` — допустимые переходы статусов.
- `src/kvitto_test/application/payments.py` — сценарий смены статуса и ошибки.
- `src/kvitto_test/repositories/payment.py` — условное обновление статуса.
- `src/kvitto_test/api/routes/webhooks.py` — проверка подписи и HTTP-ответы.
- `src/kvitto_test/core/config.py`, `.env.example` — `WEBHOOK_SECRET`.
- `tech/PROGRESS.md` — состояние слайса.

### Архитектурные решения

- Правило перехода находится в домене. Сервис сначала проверяет текущий статус,
  затем репозиторий обновляет строку только при совпадении исходного статуса.
  Конкурирующие уведомления не могут оба изменить один исходный статус.
- HMAC-SHA256 вычисляется по исходным байтам HTTP-тела и сравнивается с
  `X-Signature` через `hmac.compare_digest`. При отсутствии секрета возвращается
  HTTP 503; секрет необходимо задать через окружение или локальный `.env`.
- Транзакция завершается существующей зависимостью `get_session`. Схема БД не
