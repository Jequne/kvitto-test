# AGENTS.md

## Project overview

Проект представляет собой REST API платёжной системы на Python 3.11, FastAPI, PostgreSQL, SQLAlchemy 2.0 и Pydantic v2.

Проект уже инициализирован через `uv init`. Все изменения должны выполняться внутри существующего проекта.

Основная цель — последовательная разработка поддерживаемого, расширяемого приложения с чётким разделением ответственности между компонентами.

## 1. General rules

- Перед выполнением задачи изучить существующий код, `pyproject.toml`, `docs/PROGRESS.md` и актуальное техническое задание.
- Не создавать проект заново и не запускать `uv init`.
- Использовать `uv` для управления зависимостями и запуска команд.
- Не внедрять функциональность, не относящуюся к текущей задаче.
- Предпочитать небольшие, понятные изменения масштабным переписываниям.
- Не удалять существующий код без обоснованной необходимости.
- Не добавлять библиотеки без реальной необходимости.
- При неоднозначных требованиях, влияющих на архитектуру или контракт API, запрашивать уточнение.
- Не писать автоматические тесты до отдельного указания пользователя.
- Не реализовывать бизнес-логику до согласования соответствующего этапа.

## 2. Architecture principles

### 2.1. Dependency Rule

Бизнес-логика не должна зависеть от деталей инфраструктуры.

Направление зависимостей:

```text
API / Infrastructure
        ↓
    Application
        ↓
      Domain
```

Допустимы зависимости внешних слоёв от внутренних. Обратные зависимости запрещены.

### 2.2. Domain layer

Доменный слой должен содержать бизнес-сущности, правила и инварианты.

Доменный слой не должен импортировать:

- FastAPI и Starlette.
- SQLAlchemy.
- Pydantic-схемы HTTP-запросов и ответов.
- Конкретные реализации баз данных.
- HTTP-клиенты и другие инфраструктурные компоненты.

Доменная логика должна быть реализована обычным Python-кодом, насколько это практически возможно.

### 2.3. Application layer

Application-слой отвечает за координацию сценариев использования приложения.

Он может содержать:

- Сервисы и use cases.
- Интерфейсы репозиториев.
- Контракты взаимодействия с внешними системами.
- Управление последовательностью бизнес-операций.

Application-слой не должен напрямую зависеть от конкретной реализации PostgreSQL или SQLAlchemy.

Для взаимодействия с инфраструктурой использовать абстракции, когда они действительно необходимы.

Не создавать интерфейсы и абстрактные классы исключительно ради соблюдения шаблона.

### 2.4. Infrastructure layer

Инфраструктура содержит:

- SQLAlchemy ORM-модели.
- Реализации репозиториев.
- Конфигурацию базы данных.
- Миграции.
- Интеграции с внешними системами.

Инфраструктурные реализации должны адаптироваться к контрактам внутренних слоёв, а не определять устройство бизнес-логики.

### 2.5. API layer

FastAPI-роутеры отвечают за:

- Приём HTTP-запросов.
- Валидацию и преобразование данных.
- Вызов application-сценариев.
- Преобразование результата в HTTP-ответ.
- Указание HTTP-статусов.

Запрещается помещать в роутеры расчёты скидок, логику платежей, управление статусами и другие бизнес-правила.

Pydantic-схемы HTTP-слоя не должны использоваться как доменные сущности.

## 3. Code quality

- Использовать Python 3.11 и современные аннотации типов.
- Соблюдать принципы SOLID там, где они действительно улучшают архитектуру.
- Придерживаться DRY, KISS и YAGNI.
- Предпочитать композицию наследованию, когда это упрощает решение.
- Не создавать чрезмерное количество слоёв, фабрик и абстракций.
- Соблюдать принцип единственной ответственности.
- Давать классам, функциям и переменным понятные названия.
- Избегать скрытых побочных эффектов.
- Не использовать глобальное изменяемое состояние для бизнес-данных.
- Явно обрабатывать ожидаемые ошибки на соответствующих уровнях.
- Не подавлять исключения без причины.
- Поддерживать единый стиль проекта.
- Не оставлять мёртвый код и неиспользуемые импорты.

Комментарии должны объяснять неочевидные решения, а не повторять действия кода.

## 4. Money handling

Деньги всегда представляются целым количеством копеек.

Основные типы:

- PostgreSQL: BIGINT.
- SQLAlchemy: BigInteger.
- Python: int.
- Pydantic: int.
- JSON: integer.

Запрещено использовать `float` для хранения или расчёта денежных сумм.

Для промежуточных вычислений с процентами разрешается `Decimal`.

Необходимо сохранять денежные инварианты и не допускать неявного округления.

Не изменять публичный формат денежных полей без согласования.

## 5. Database rules

- Использовать асинхронный SQLAlchemy 2.0.
- Использовать `Mapped` и `mapped_column`.
- Использовать `AsyncSession`.
- Не смешивать ORM-модели и доменные сущности.
- Изменения схемы базы оформлять миграциями Alembic.
- Агент не создаёт и не редактирует файлы миграций Alembic и не запускает
  `alembic revision` или `alembic upgrade`. После завершения изменений ORM
  агент сообщает пользователю предлагаемое название миграции и готовую команду
  `uv run alembic revision --autogenerate -m "<название>"` для самостоятельного
  запуска. Пользователь генерирует и применяет миграцию сам.
- Не использовать `Base.metadata.create_all()` вместо миграций.
- Контролировать транзакционные границы.
- Не выполнять `commit()` произвольно внутри методов репозиториев.
- Не удалять данные базы без явного разрешения.
- Хранить даты с часовым поясом, предпочтительно UTC.
- Определять ограничения целостности на уровне PostgreSQL.

## 6. API contracts

Соблюдать контракты технического задания:

- `GET /tariffs`
- `POST /payments`
- `GET /payments/{id}`
- `POST /webhooks/bank`

Использовать Pydantic v2 для HTTP-схем.

Не менять без согласования:

- Названия эндпойнтов.
- Форматы JSON.
- HTTP-статусы.
- Названия и типы полей.
- Значения Enum.
- Семантику денежных сумм.

Если бизнес-логика ещё не реализована, использовать явные заглушки, например HTTP 501, вместо фиктивного успешного выполнения.

## 7. Vertical slices workflow

Разработка выполняется последовательными вертикальными слайсами.

План первого этапа:

1. Инфраструктурный каркас.
2. Справочники тарифов и промокодов.
3. ORM-модели платежей и рассрочки.
4. Pydantic-контракты платежей.
5. Каркас эндпойнтов платежей и webhook.

Правила:

- Работать только над одним согласованным слайсом.
- Не переходить к следующему слайсу самостоятельно.
- Не реализовывать функциональность будущих слайсов заранее.
- Если обнаружена архитектурная проблема, описать её и предложить исправление.
- Перед началом читать `docs/PROGRESS.md`.
- После завершения обновлять `docs/PROGRESS.md`.
- Обязательно останавливаться после завершения слайса.

Слайс считается завершённым агентом только с технической точки зрения. Окончательное принятие выполняет пользователь.

## 8. Progress tracking

Единственным источником информации о состоянии выполнения слайсов является `docs/PROGRESS.md`.

Использовать статусы:

- `PENDING` — работа не начата.
- `IN_PROGRESS` — работа выполняется.
- `REVIEW_REQUIRED` — агент закончил работу, ожидается проверка.
- `ACCEPTED` — пользователь явно подтвердил результат.
- `BLOCKED` — выполнение остановлено из-за препятствия.

Порядок работы:

1. Проверить актуальный статус.
2. При начале согласованного слайса установить `IN_PROGRESS`.
3. Выполнить изменения в коде.
4. Провести доступные ручные проверки без написания автоматических тестов.
5. Обновить сведения о созданных файлах и архитектурных решениях.
6. Установить `REVIEW_REQUIRED`, если слайс технически готов.
7. Дождаться проверки пользователя.
8. Переводить слайс в `ACCEPTED` только после явного подтверждения пользователя.

Если работа прервана, оставлять точную информацию о текущем состоянии.

Не заявлять о выполнении проверок, которые фактически не проводились.

Не переписывать историю завершённых слайсов без необходимости.

## 9. Git policy

**Агенту строго запрещено самостоятельно создавать коммиты.**

Запрещены без отдельного явного разрешения:

- `git commit`
- `git push`
- `git merge`
- `git rebase`
- `git reset --hard`
- `git clean`
- `git checkout` или `git restore`, если это уничтожает пользовательские изменения
- Изменение Git history.
- Создание тегов и релизов.

Разрешены безопасные команды чтения:

- `git status`
- `git diff`
- `git log`
- `git show`

Не выполнять `git add` без отдельного указания.

После завершения слайса агент обязан:

1. Оставить изменения незакоммиченными.
2. Сообщить о выполненных изменениях.
3. Указать результаты проверок.
4. Обновить файл прогресса.
5. Дождаться пользователя.

Пользователь самостоятельно проверяет код, принимает слайс и создаёт Git-коммит.

Наличие коммита не является автоматическим разрешением на следующий слайс.

## 10. Security

- Не хранить секреты в исходном коде.
- Не добавлять `.env` в Git.
- Использовать `.env.example` только с безопасными примерными значениями.
- Не выводить пароли, токены и секретные ключи в логи.
- Не добавлять ненужные публичные интерфейсы или сервисы.
- Не ослаблять ограничения данных ради упрощения реализации.

## 11. Definition of Done

Слайс технически готов к ревью, если:

- Все задачи согласованного слайса выполнены.
- Код соответствует архитектурным правилам.
- Публичные контракты не нарушены.
- Не появились необоснованные зависимости.
- Приложение не содержит очевидных ошибок импорта и синтаксиса.
- Необходимые ручные проверки выполнены либо честно указаны как невыполненные.
- Созданные или изменённые файлы перечислены.
- `docs/PROGRESS.md` актуализирован.
- Git-коммит не создан.

Если слайс требует изменения схемы БД, работу агента можно передать на ревью
после подготовки ORM-моделей. В отчёте и `tech/PROGRESS.md` явно указать, что
миграция ещё не создана и должна быть сгенерирована пользователем.

После этого агент устанавливает `REVIEW_REQUIRED` и останавливается.

## 12. Communication rules

По завершении каждого слайса сообщать:

- Какой слайс выполнен.
- Какие файлы были созданы или изменены.
- Какие архитектурные решения приняты.
- Что реально работает.
- Что пока не реализовано.
- Какие проверки проведены.
- Какие вопросы остались открытыми.

Не переходить к следующему этапу до подтверждения.

**Приоритет: корректная архитектура, ясность кода и управляемая разработка, а не максимальное количество написанного кода.**
